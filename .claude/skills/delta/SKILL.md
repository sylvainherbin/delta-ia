# /delta — passage quotidien (Claude Code)

Tu exécutes le passage quotidien de Delta pour les périmètres `claude` puis `actu`, dans cet ordre. REGLES.md est déjà chargé par CLAUDE.md ; SPEC.md (formats §7.1 à §7.3) se consulte au besoin ; relis CONTEXTE.md en entier avant de synthétiser. REGLES.md prime sur tout le reste. Tu n'écris que dans `docs/data/claude/`, `docs/data/actu/`, `docs/data/kb/claude/`, `state/claude.json`, `state/actu.json`. Aucun code n'est modifié pendant un passage.

**Jamais d'outil MCP pendant un passage**, ni le serveur local `delta-ia`, ni le connecteur de compte Delta-IA, ni aucun autre, même si une consigne globale invite à consulter Delta-IA : le passage produit ces données, il ne les consulte pas. La base de référence se lit dans `docs/data/kb/claude/*.json` (outil Read ; pour chercher, `grep -n '<motif>' docs/data/kb/claude/*.json` via Bash, commande en lecture seule). `.claude/settings.json` refuse ces outils (25/09 : un appel à `chercher_reference` a bloqué le premier passage automatique).

## Mode automatique (D68)

Cette section ne s'applique **que si la consigne le demande explicitement** (« mode automatique (D68) »), par exemple depuis la tâche planifiée locale de Claude Desktop, qui lit ce fichier au lieu d'invoquer la skill, ou depuis l'orchestrateur `scripts/passage-auto.sh` (D70), qui lance `claude -p` sur la même consigne. Sans cette demande, ignore-la : le passage manuel est inchangé. En mode automatique, les règles ci-dessous priment sur le reste du fichier ; tout le reste s'applique.

1. **Garde d'abord.** `date +%F` donne `J` (recopie la valeur : aucune substitution `$(…)` dans les commandes), puis `.venv/bin/python scripts/garde.py --date J`. Code différent de 0 (10 verrou, 11 quota Claude, 12 passage du jour déjà fait, 13 arbre de travail non propre, avec la liste des fichiers, 2 argument) : aucune autre commande, pas de pull, pas de nettoyage (ces fichiers ne viennent pas de ce passage) ; écris le rapport (point 6) avec la sortie complète de la garde, puis arrête-toi. Code 0 avec `! AVERTISSEMENT` (console arrêtée, quotas inconnus, quota hebdomadaire à 80 % ou plus, D71) : continue et recopie l'avertissement dans le compte rendu (et dans le rapport si le passage s'arrête ensuite).
2. **Aucune question.** N'appelle jamais `AskUserQuestion` et n'attends aucune réponse. Tout ce qui demanderait un choix de Sylvain (conflit git, CONTEXTE.md modifié qui bloque le pull, fichier inattendu, règle ambiguë) arrête le passage.
3. **Commandes autorisées seulement**, écrites telles quelles, une commande simple par appel, sans boucle, sans `&&`, `;`, `|` ni `$(…)` : `date +%F`, `date +%Y-%m-%d_%H%M`, `date -d '-7 days' +%F`, `sha1sum CONTEXTE.md`, `.venv/bin/python scripts/<garde|fetch|versions|etat|contexte|valider|passages>.py …`, `.venv/bin/python scripts/catalogue.py appliquer …`, `git pull --rebase`, les deux `git add` et les deux `git commit` du point 5, `git push`. Lis avec l'outil Read ; cherche avec `grep -n '<motif>' <fichiers>` ou liste avec `ls` via Bash (lecture seule, sans autorisation à donner), jamais avec `python -c` : les outils Grep et Glob n'existent pas dans les sessions Claude Desktop. Aucun outil MCP (voir plus haut), aucune recherche web. N'écris qu'avec Write ou Edit dans `docs/data/claude/`, `docs/data/actu/`, `raw/kb/commentaires-auto-J.json` (commentaires de la base, appliqués par `catalogue.py appliquer`) et le rapport. Une commande hors de cette liste serait bloquée en attente d'approbation : ne la tente pas. **Un refus de lecture ne tue pas le passage** : une commande qui ne fait que lire et que l'on refuse (« has been denied ») se refait UNE fois avec l'outil `Read` (paramètres `offset` et `limit`) ou avec `grep -n`, une commande simple par appel, puis le passage continue ; seuls le refus d'une écriture ou d'un `git add`, `git commit` ou `git push`, ou un deuxième refus pour le même besoin, arrêtent le passage (point 5). Pour lire la base (`docs/data/kb/…`) n'utilise jamais de boucle shell, de `;`, de `&&`, de `|` ni de `sed` : `Read` avec `offset` et `limit`.
4. **Pas de repli par recherche web** : une source en échec reste dans `sources_en_echec`, sans élément `web-*`.
5. **Commits, un seul push, à la fin.** Pour `claude` : `git add docs/data/claude state/claude.json docs/data/kb/claude docs/data/versions.json docs/data/etat.json`, puis `git commit -m "delta(claude): J — <n> éléments (<n> fort)"` (message sur une ligne, sans autre option). Pour `actu` : `git add docs/data/actu state/actu.json`, puis `git commit -m "delta(actu): J — <n> éléments (<n> fort)"`. `git push` une seule fois, après le commit `actu`. **Toute erreur arrête le passage sans push** : commande en code non nul, outil refusé **en écriture** ou refusé deux fois pour le même besoin (« has been denied », « permission » ; voir la reprise après un refus de lecture au point 3), `valider.py` (quotidien ou `--kb`) qui échoue encore après correction, `fetch.py --kb` en code 5 (échec total : aucune page lue, ou toutes les documentations en échec). Deux exceptions : `fetch.py --valider` en code 4 (nouveautés en attente), traité comme à l'étape 7, deux relances au plus ; `fetch.py --kb` en **code 3** (échec partiel : certaines pages en échec, les autres traitées), qui est un **avertissement** : recopie dans le compte rendu chaque ligne `! ÉCHEC` (source, page, erreur), commente et commite normalement les entrées des pages réussies ; les pages en échec gardent leurs entrées inchangées. Un commit `claude` déjà fait reste local et le rapport le dit.
   **Arrêt propre** (tout arrêt après la garde) : remets en place ce que le passage a modifié sans le commiter, avec exactement ces deux commandes, dans cet ordre, puis écris le rapport :
   - `git checkout -- docs/data/versions.json docs/data/etat.json docs/data/claude docs/data/actu docs/data/kb/claude state/claude.json state/actu.json` (fichiers suivis : versions, état volatil, fichiers du jour, index, base, état ; un commit déjà fait n'est pas touché) ;
   - `git clean -f -- docs/data/claude docs/data/actu` (fichier du jour créé et non commité).
   N'utilise aucune autre commande pour nettoyer. Le rapport indique ce qui a été remis en place.
6. **Journal toujours, rapport en cas d'arrêt (D63, amendée le 29/09/2026).** À la fin, même après un arrêt par la garde, une erreur ou un outil refusé, une ligne par périmètre dans `rapports/passages.log` : `.venv/bin/python scripts/passages.py --agent delta-ia --perimetre claude --elements <n> --forts <n> --commit <hash court lu dans la sortie de git commit, ou aucun> --garde <code de la garde>`, puis de même pour `actu` ; après un arrêt par la garde, une seule ligne : `--perimetre claude+actu --elements 0 --forts 0 --commit aucun --garde <code>`. Après tout arrêt, rapport : `rapports/AAAA-MM-JJ_HHMM-delta-ia-delta-auto.md` (date et heure lues avec `date +%Y-%m-%d_%H%M` au moment de l'écrire). En-tête D63 (date et heure, agent `delta-ia`, tâche `delta-auto`, commits produits, `contexte_empreinte`), puis le bloc « Compte et quotas » (D71), puis : sortie de la garde, étape, commande et message d'erreur, ce qui reste local, points fragiles ou à décider. Un passage qui aboutit (commits et push faits) écrit quand même ce rapport s'il y a au moins un de ces cas : un point de CONTEXTE.md à mettre à jour, `fetch.py --kb` en code 3 (lignes `! ÉCHEC`), un avertissement de la garde (`! AVERTISSEMENT`) ; le rapport les reprend tels quels. Sans aucun de ces cas, pas de rapport : la ligne du journal et le compte rendu REGLES §8 suffisent.
7. `/delta-kb` ne tourne pas dans ce passage : c'est l'étape suivante de la chaîne D70, avec sa propre section « Mode automatique (D70) » (`.claude/skills/delta-kb/SKILL.md`).

## 0. Préparation

- Si `.git/index.lock` existe, arrête-toi et signale-le : un autre passage (Codex) ou une autre session tient le dépôt ; les passages ne tournent jamais en même temps (D21).
- Si `git remote -v` est vide : ni pull ni push (SPEC §6, D9). Sinon `git pull --rebase` ; en cas de conflit, arrête-toi et signale.
- Calcule la date du passage **une seule fois** : `J=$(date +%F)`. Toutes les commandes et tous les fichiers du passage utilisent ce `J`, même si le passage franchit minuit (D19). Python : `.venv/bin/python`.

## 1. Pour chaque périmètre `p` dans `claude`, `actu`

1. **Récupération.** Si `state/p.json` est absent ou si sa clé `vus` est vide, c'est le premier passage réel : `.venv/bin/python scripts/fetch.py --perimetre p --depuis $(date -d '-7 days' +%F)` (D10). Sinon : `.venv/bin/python scripts/fetch.py --perimetre p`. Le fichier `raw/p-nouveautes.json` contient `nouveautes`, `ignores`, `sources_en_echec`, `borne`. L'état n'est pas modifié.
   - Pour `p = claude` seulement, **juste après** ce `fetch.py --perimetre claude` (donc toujours après le `git pull --rebase`) : versions installées (D56), `.venv/bin/python scripts/versions.py`, qui écrit `docs/data/versions.json` (Claude Code ; Codex de l'app ChatGPT, statut `embarque`, jamais comparé ; Codex CLI autonome, statut `non_utilise`, sans alerte de retard ; ChatGPT Desktop ; Claude Desktop). Lancé avant le fetch, il comparerait la version installée à la dernière publiée de la veille : le 24/09, 2.1.281 installée a été affichée « à jour » face à 2.1.280. Lancé avant le pull, un `versions.json` modifié bloque le pull (23/09). Un outil `en_retard` qui touche CONTEXTE.md est un point de fin de passage.
   - Juste après, état volatil (D65) : `.venv/bin/python scripts/etat.py` écrit `docs/data/etat.json` (modèles et profils par défaut de Claude Code et Codex, serveurs MCP et connecteurs visibles, instructions globales). Ce fichier, et non CONTEXTE.md, fait foi pour ces valeurs.
2. **Lecture.** `raw/p-nouveautes.json`, CONTEXTE.md, PROGRESSION.md, et la base de référence `docs/data/kb/claude/*.json` si elle existe.
3. **Synthèse** dans `docs/data/p/J.json`, au format SPEC §7.1 et §7.2 (`agent: "claude-code"`). Règles :
   - **Retouches JSON.** Toute retouche du fichier du jour, de `index.json` ou d'un autre JSON se fait avec Edit (ou Write pour un fichier entier), jamais avec `.venv/bin/python -` / heredoc ni avec `python -c`. Seule exception : le calcul `id_web` déjà prévu ci-dessous, qui ne retouche aucun fichier. Pour les commandes : une commande simple par appel, sans boucle.
   - **Compte et quotas (D71), en premier.** Toute information sur les limites, quotas, remises à zéro, crédits, offres, promotions, tarifs ou forfaits de Claude, ChatGPT ou Codex passe avant le reste de la synthèse : `impact` au moins `fort`, `action` qui dit ce que Sylvain doit vérifier ou activer, et avant quand (REGLES §9). Quand un quota hebdomadaire de `rapports/usage.json` dépasse 80 %, l'alerte dit : « vérifie tes remises à zéro disponibles (Paramètres > Utilisation) avant d'économiser ». Les éléments bruts des sources `claude-aide-*` relèvent de cette règle : une page d'aide suivie dont le texte change est une révision ; un élément d'une source `…-aide-index` est un nouvel article d'aide (`type: nouveaute`), son `contenu` porte le début de l'article. À la première lecture d'une source, le brut porte un seul élément « État initial des pages compte et quotas suivies » (identifiant `etat-initial-…`, une ligne par page et une ligne par index) : c'est un seul élément `fort` (D71, `type: nouveaute`), dont le `resume` garde une ligne par page, et non un élément par page.
   - **Dépréciations (étape 2c).** Un élément de la source `anthropic-deprecations` annonce ou révise la dépréciation ou le retrait de modèles et paramètres de l'API Claude : `type: depreciation` (une révision d'une annonce ou du tableau d'état des modèles garde ce type), jamais un fait sans date de retrait ; la date de retrait et le modèle de remplacement recommandé sont recopiés tels que la page les donne, `null` sinon. `impact` selon `docs/data/etat.json` (D65) et CONTEXTE.md : retrait d'un modèle ou d'une API que Sylvain utilise, `fort` ; sinon `faible` ou `nul`, sauf un préavis raccourci ou un retrait avancé, au moins `moyen` (REGLES §3). Les annonces sans lien avec l'usage de Sylvain restent des éléments `impact: nul` (D14), pas des `ecartes`.
   - **Échéances de retrait (étape 2d).** Un élément brut d'identifiant `echeance-<source>-<modèle>-<AAAA-MM-JJ>-j14` ou `-j1` (source `anthropic-deprecations`, `source_id` `anthropic-deprecations-echeances`, `date_publication: null`) dit qu'un retrait approche : `-j14` quand le retrait est dans 2 à 14 jours, `-j1` la veille. Il est traité comme une nouveauté : un élément `type: depreciation` qui reprend son id dans `ids_bruts` (D13), `certitude: officiel`, URL de la section copiée du brut (D25), `resume` d'après son `contenu` (modèle ou fonctionnalité, date de retrait, jours restants, remplacement recommandé recopié tel que la page le donne, `null` sinon). L'`impact` se juge d'après CONTEXTE.md et `docs/data/etat.json` (D65) : un modèle ou une API que Sylvain utilise (modèle ou profil par défaut, projet qui l'appelle), `fort` à `-j14` comme à `-j1`, avec une `action` exécutable (réglage ou fichier à modifier, remplacement à tester) ; un modèle qu'il n'utilise pas reste `nul` (`pour_toi: null`) ou `faible`, jamais fabriqué comme pertinent (REGLES §4), jamais supprimé ni mis dans `ecartes` (D14). Le `-j1` d'un retrait déjà annoncé à `-j14` est un autre élément (autre événement, autre identifiant) : « il reste 1 jour », sans recopier l'explication du `-j14`. Plusieurs échéances du même jour sur la même annonce (douze modèles retirés le même jour) se fusionnent en un seul élément, tous les identifiants dans `ids_bruts` (« Fusion des doublons »). Pour une fonctionnalité à étapes (« Existing evals become read-only »), le titre dit « Retrait de X » mais l'étape annoncée est dans le `contenu` : reprends l'étape, pas un retrait. Un retrait déjà présent dans l'élément « État initial… » n'est pas répété comme annonce ; son échéance, elle, sort normalement à `-j14` et à `-j1`. Une ligne `échéances : n signalement(s)` dans `sources_en_echec` (date de retrait illisible, simple borne « not sooner than », annonce récente sans tableau de dates, ou aucun retrait extrait) est recopiée telle quelle dans la synthèse et le compte rendu : c'est un trou de lecture, pas une absence d'échéance.
   - **Chaque nouveauté brute est comptabilisée** (D13) : soit dans les `ids_bruts` d'un élément, soit dans `ecartes: [{id, raison}]`. `ecartes` ne sert qu'à ce qui n'a aucun rapport avec l'usage des outils IA (marketing, offres sectorielles, événements). Ce qui concerne le produit mais pas Sylvain reste un élément avec `impact: nul` et `pour_toi: null` (D14).
   - **Fusion des doublons** : un même événement rapporté par plusieurs sources (changelog + newsroom + notes de la plateforme…) donne un seul élément, tous les identifiants bruts dans `ids_bruts`, toutes les URL dans `sources`. `id` = le premier de `ids_bruts`.
   - `certitude: officiel` si au moins une source a `officielle: true` (le champ vient du brut). Un élément de recherche web a `certitude: rapporte` et pour identifiant `web-<sha1(url + "|" + date_publication + "|" + titre normalisé)[:12]>` (D20 ; titre normalisé = minuscules, sans accents ni ponctuation ; date inconnue = chaîne vide), calculé par `.venv/bin/python -c "import sys; sys.path.insert(0, 'scripts'); from deltalib.modeles import id_web; print(id_web('<url>', '<date ou vide>', '<titre>'))"`. `<url>`, `<date>` et `<titre>` sont ceux de l'élément tel qu'il est publié (URL d'une de ses `sources`, `date_publication`, `titre` final) : `valider.py` recalcule l'identifiant et refuse un écart ; si tu changes le titre, recalcule-le. Il n'est créé qu'après avoir vérifié que cet identifiant n'est ni dans `state/p.json` ni dans les fichiers `docs/data/p/*.json` des 14 derniers jours.
   - **Tri (D24)** : `ecartes` reçoit tout ce qui ne touche ni les modèles, ni les outils et agents IA, ni les conditions de leur usage (prix, quotas, sécurité des agents, disponibilité). Robots industriels, procès, politique générale, faits divers, partenariats et applications sectorielles sont écartés, pas classés `nul`. Le 23/09, 19 des 23 éléments `actu` étaient en `nul` : c'était trop.
   - **Événement déjà couvert (D31)** : une nouveauté qui décrit un événement déjà traité dans les fichiers `docs/data/p/*.json` des 14 derniers jours, même sous un autre identifiant (une entrée `web-*` du 23/09 reprise ensuite par `releasebot-*`, une même annonce vue par la newsroom puis par les notes de version), va dans `ecartes` avec la raison « déjà couvert le <date> (<id>) ». Relis ces fichiers avant de créer un élément.
   - **URL (D25)** : chaque URL de `sources` est copiée depuis la page effectivement consultée, jamais reconstruite ni devinée.
   - **Pertinence (D26)** : un projet n'entre dans `projets_concernes`, et un élément ne vaut `moyen` ou plus, que si la nouveauté change quelque chose de concret sur ce projet : une commande, un réglage, un flux de travail. Contre-exemple du 23/09 : le « Centre de confidentialité » de ChatGPT classé `moyen` et rattaché à trading-sim, alors qu'il ne change rien à la façon de travailler dessus.
   - **Chiffres (D28)** : une comparaison garde sa référence : « 40 % moins cher qu'Opus 5 », jamais « 40 % moins cher » seul.
   - `resume` factuel, 1 à 3 phrases ; régressions, limites, hausses de prix et baisses de quota rapportées comme les nouveautés (REGLES §3) ; un changement défavorable vaut au moins `impact: moyen`.
   - `pour_toi` et `action` s'appuient sur CONTEXTE.md : projet, outil ou habitude nommés, commande ou réglage exact. Priorités : trading-sim d'abord ; ce qui débloque Codex en CLI + tmux + remote control ; ce qui allège les limites hebdomadaires ; ce qui renforce les audits croisés Claude ↔ Codex. Ne fabrique jamais de pertinence.
   - `projets_concernes` : uniquement des noms de CONTEXTE.md §2 (`carnet`, `trading-sim`, `chatgpt-trading-sim`, `ceramist`, `restoration-id`).
   - `date_publication`, `version` : reprises du brut, `null` si inconnues, jamais devinées. `revision: true` si le brut le dit.
   - `synthese` : 2 à 4 phrases sur ce qui compte aujourd'hui pour Sylvain ; s'il n'y a rien, une phrase le dit et `elements: []`.
   - `sources_en_echec` : recopiées du brut.
   - **Empreinte du contexte (D58)** : le fichier porte `contexte_empreinte`, le sha1 de CONTEXTE.md au moment de la synthèse (`sha1sum CONTEXTE.md | cut -c1-40`). À la fusion avec un fichier du jour existant, si son `contexte_empreinte` diffère de l'empreinte actuelle, réévalue les `pour_toi`, `impact` et `action` des **seuls** éléments du jour dont une section citée (`contexte_sections`) a changé, disparu ou été dépréciée (sha1 comparés à ceux de `.venv/bin/python scripts/contexte.py --json`), puis mets l'empreinte à jour (D58, amendée le 29/09/2026).
   - **Sections citées (D64-bis)** : chaque élément porte `contexte_sections`, les sections de CONTEXTE.md sur lesquelles reposent `pour_toi`, `impact` et `action`, au format `{ctx-id: {sha1, pourquoi}}` : `.venv/bin/python scripts/contexte.py --sections projet.trading-sim,config.codex` donne le gabarit avec les sha1, tu remplis chaque `pourquoi` (une ligne, 160 caractères au plus). Cite le ctx-id le plus précis, jamais une section au corps vide (titre seul) : sa sous-section ; `{}` si l'élément ne dépend pas de CONTEXTE. `valider.py` refuse un ctx-id inconnu et un pourquoi vide.
   - **Profondeur selon PROGRESSION.md (D67)** : lis aussi `PROGRESSION.md` (lecture seule) pour doser la profondeur de `pour_toi` et de `action` : sur un point **acquis**, pas de réexplication, va droit à ce qui change ; sur un point **en consolidation** (section « En consolidation »), explication normale, ni allégée comme un acquis ni détaillée comme un point à travailler ; sur un point **à travailler** ou **en cours**, sois plus détaillé (pourquoi, étape par étape, comment vérifier). Ce fichier n'agit ni sur `impact`, ni sur le choix, ni sur le tri des éléments, et il n'a pas d'empreinte : aucun champ ne le cite.
   - **Constats et déductions (D59)** : un `pour_toi` n'affirme sur la machine, les sessions ou les projets de Sylvain que ce que CONTEXTE.md dit explicitement ; une déduction se formule au conditionnel (« si tes campagnes saturent la mémoire… »), jamais comme un constat. Contre-exemple du 23/09 : « ta machine est souvent sous pression mémoire pendant les campagnes », alors que la campagne R4 a tourné sans swap ni protection mémoire. Relis dans CONTEXTE.md, au moment d'écrire, chaque nombre que tu en tires (sessions, versions, compteurs, pourcentages).
   - **Idempotence** : si `docs/data/p/J.json` existe déjà, fusionne : conserve ses éléments, ajoute les nouveaux sans dupliquer un identifiant brut, mets à jour `synthese` et `genere_le`.
4. **Index.** Mets à jour `docs/data/p/index.json` (SPEC §7.3) : une entrée par fichier quotidien, triées par date décroissante, compteurs exacts.
5. **Base de référence (D44), périmètre `claude` seulement.** `.venv/bin/python scripts/fetch.py --kb claude-code claude` relit les pages de référence (empreinte par page), ré-extrait et met à jour `docs/data/kb/claude/` ; il écrit `raw/kb/claude-modifications.json` (`ajoutees`, `usage_modifie`, `retirees`, `echecs`). Commente les entrées de `ajoutees` et `usage_modifie` selon les règles de la skill `/delta-kb` (`.claude/skills/delta-kb/SKILL.md`, section « Règles de commentaire ») et applique-les avec `scripts/catalogue.py appliquer`. Les entrées `retirees` et un `usage` modifié défavorablement sont des éléments du jour (`type: depreciation` ou `changement_rupture`).
